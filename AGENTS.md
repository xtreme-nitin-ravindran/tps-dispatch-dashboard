# Repository workflow

## Branching and publication

- Make code changes on `dev`. Do not commit or push application code directly to `main`.
- Pushes to `dev` are promoted automatically through a protected PR only after required checks pass. Do not bypass branch protection or force push.
- Do not push unless the user explicitly authorizes publication.
- Pull `origin/dev` with fast-forward only before new work, because automatic promotion may advance it.
- `data/current.json` is generated by the data pipelines and published to Cloudflare R2; the separate `data` branch was retired. Do not include generated snapshot edits in code commits on `dev` unless the task explicitly requires changing snapshot output.
- Documentation-only changes may skip the expensive application test steps, but only through the conservative classifier in `scripts/docs-only.js`. It is allow-list based (documentation extensions in `docs/` or an explicit root documentation file) and rejects any candidate that executable tooling references, so a Markdown extension alone is never sufficient. Mixed changes and all application, script, test, fixture, workflow, package, Docker, deployment/configuration, and generated-data changes keep full validation. Renames and deletions are conservative: both the old and new path must qualify. The `changes` job always runs and the `tests` job always reaches a terminal result, so a required status context is never left pending. Do not replace this with a workflow-level `paths-ignore`, which would leave promotion waiting indefinitely.

## Change discipline

- Make the smallest change necessary for the requested task.
- Do not refactor, redesign, or clean up unrelated code.
- Preserve existing behavior outside the requested scope.
- Reuse existing state, rendering, DOM, and data paths instead of introducing duplicate implementations.
- Every map popup surface (road closures, TTC disruptions, incident markers) opens and closes through the `src/map-popups.js` controller (`createMapPopups`); add new popup surfaces through it instead of calling Leaflet `bindPopup`/`openPopup` directly, so the single-bubble and immediate-teardown contract stays structural.
- TTC detail nodes come from `createTtcDetail(item, { variant })` (`'card'` for list/disclosure bodies, `'detail'` for the mobile sheet and both bubbles); app-side call sites go through the shared `ttcDetailFor()` helper so the contexts cannot drift.
- Remove legacy or duplicate code only when it is demonstrably dead or directly relevant to the task.
- Do not make speculative fixes before identifying the actual failure or root cause when reproduction is practical.
- Small changes should produce small diffs. Unexpected large diffs are a stop condition and must be investigated before continuing.
- After extracting code out of `src/app/app.js`, run `npm run verify:fast` without file arguments: the source-text pins live in many test files and targeted runs miss them.
- When repointing a source-text pin at a newly extracted module, verify the pin's source variable was actually declared in that test file. Some tests read sources with top-level `await readFile` (`node:fs/promises`) instead of `readFileSync`, and a declaration insert can silently miss the async form.

## UI design confirmation and visible acceptance

- Before implementing UI changes, show concise ASCII line-art sketches of the proposed layout, labels, and relevant states so the developer can confirm what they want. When alternatives matter, label them clearly and explain any effect on existing layout or measured stacking. Wait for the developer's selection before implementing; an already selected sketch satisfies this step unless the design changes materially.
- For acceptance criteria that surface information in a map-layer status or other UI element, inspect the existing CSS and verify the cue is actually visible in the rendered browser at applicable breakpoints. Updating DOM text alone does not establish visible acceptance; check clipping, dimensions, overflow, and stacking.
- Story 53B precedent: Story 41A clips `#roadOverlayStatus` to 1×1 via `.map-layer-toggle .map-layer-status`. The B2 repair disclosure belongs in the visible `#roadOverlayLabel` (for example, `Road closures · source repaired`), preserving the existing control stack and accessible status. Confirm the current markup and styles before reusing this pattern.
- Story 74 precedent: computed geometry, not DOM text, is visible-acceptance evidence. A chrome class reused on an element that already carries competing class rules is a cascade hazard — a later equal-specificity `.disruption-item { padding: 14px 0 }` overrode `.closure-detail`'s 16px padding inside Leaflet popups, and the defect survived a review round because the check stopped at DOM structure. When chrome classes span contexts (list, sheet, popup), scope the overrides (for example `.leaflet-popup-content .closure-detail`) and have the rendered-browser suite assert measured padding, margins, and edge offsets (the article's `getBoundingClientRect()` against its content box), not only presence and text.
- Story 75 precedent: when a shared-chrome rule clips a whole subtree (Story 40D's `.leaflet-control-layers-overlays label[data-mobile-label] > span > span { clip-path: inset(50%) }`), un-clip the element that actually matches the selector — the wrapper — and reset its `width`/`height`, not only its leaf descendants.

## Docker and local validation

- Use Docker for repository validation commands.
- Do not use port `8080`.
- During implementation, prefer the smallest relevant targeted test set, or `npm run verify:fast` (or `npm run verify:fast -- test/file.test.js`) for a fast inner-loop check.
- The canonical test image is named `toronto-dispatch-tests`. `scripts/docker-test.sh --ensure-image` prints one concise readiness line naming that image when it already exists and its fingerprint is current; use its exit status as the authoritative signal.
- Run repository Node, ESLint, and Ruff validation through `scripts/docker-test.sh`, `npm run verify:fast`, or `npm run verify`. Do not use a missing or different host toolchain to diagnose a failure unless the same failure reproduces in the canonical Docker environment. Host-only failures still need a follow-up when the host version is within `package.json`'s supported `engines` range.
- Do not repeatedly run the full repository suite after every small change.
- Run broad/full verification at story or feature completion, or when required to reproduce a CI failure. Use `npm run verify` for final full validation; it is the single, versioned entry point for every required check. Continue to use the smallest relevant targeted checks during implementation.
- `npm run verify` runs its independent checks concurrently with bounded concurrency (`VERIFY_JOBS`, default `4`, maximum `8`); image preparation and the Git/snapshot checks stay sequential and run before the independent jobs (a trivial whitespace or snapshot failure surfaces in about a second instead of after the full pipeline). Every required check still runs exactly once. Set `VERIFY_JOBS=1` for fully sequential, readable diagnosis. An invalid `VERIFY_JOBS` value is rejected before any Docker work.
- `npm run verify:fast` is an inner-loop aid only. It ensures the Docker test image exists and is current, runs full lint and the browser syntax checks, and runs offline unit tests under `TZ=UTC`, but it omits the America/Los_Angeles suite, the Python tests, the live-source integration suite, the coverage gate, and the Git publication/snapshot checks. It does not satisfy the 100/100/100 coverage requirement and is not final, pre-push, or promotion verification.
- `npm test` and `npm run test:coverage` both run the canonical offline suite through `scripts/run-unit-tests.sh`. That runner is the single source of truth for which offline JavaScript test files run: it selects every `test/*.test.js` file, excludes every `test/*.integration.test.js` live-source test, and sorts the result deterministically. Do not reintroduce a manually duplicated file list in `package.json`; new offline `*.test.js` files join the suite automatically. `npm run test:coverage` runs that same file set with Node coverage and the mandatory 100/100/100 gate. Live-source integration tests run only under `npm run test:integration`; browser/Playwright suites run only under their `test:*:browser` scripts.
- Before declaring a task complete, verify that `git diff --stat` and `git diff` contain only intentional changes.

### Docker test image freshness and the working-tree wrapper

Validation runs through `scripts/docker-test.sh`, which mounts the current
working tree read-only over the image's `/workspace` while keeping the
image-installed `node_modules` and pinned tools (Node, ESLint, Ruff). The image
is a dependency/tooling snapshot, not a source snapshot.

- **Mandatory validation note:** Run `npx eslint .`, not only targeted files. Rendered-browser validation runs through `npm run test:browser`, which includes the TTC UI suite and does not rely on GNU `timeout`.
- Source, test, fixture, script, and bind-mounted configuration edits do **not**
  require a Docker rebuild. The wrapper supplies the current working-tree content
  on every run.
- Run validation through `scripts/docker-test.sh`, `npm run verify:fast`, or
  `npm run verify`. Do not call `docker run` directly for validation; a bare
  `docker run` uses the image's baked-in source and can silently validate old code.
- Rebuilding remains mandatory when the Dockerfile or the dependency/tooling
  fingerprint inputs change: `docker/Dockerfile.test`, `docker/Dockerfile.test.dockerignore`, `package.json`,
  and `package-lock.json`. Build with the canonical path:
  `scripts/docker-test.sh --build`.
- The wrapper computes a SHA-256 fingerprint of those inputs and compares it with
  the `org.sirento.test-fingerprint` label baked into the image. On mismatch it
  fails before testing with a clear rebuild command. `npm run verify` and
  `npm run verify:fast` call `scripts/docker-test.sh --ensure-image`, which builds
  only when the image is missing or stale.
- A commit-derived image tag alone does **not** detect uncommitted dependency
  changes, because the commit hash does not change. The fingerprint is
  content-derived, so uncommitted `package.json`/`package-lock.json`/`docker/Dockerfile.test`/
  `docker/Dockerfile.test.dockerignore` edits are detected.
- Keep the image cheap to rebuild: `npm ci` must stay in its own layer with only
  the manifests copied before it, and repository content must be copied from
  relatively stable to relatively volatile (`concourse`, `.github`, `data`,
  `scripts`, `src`, `test`, `assets`, then the root hosting entry files). Do not add a broad `COPY . .`.
  `docker/Dockerfile.test.dockerignore` must exclude only non-build inputs and must never exclude a
  path the Dockerfile copies. `test/docker-image-layout.test.js` enforces these
  properties structurally.
- When a local Docker result disagrees with CI, first run the wrapper's
  fingerprint check (`scripts/docker-test.sh --fingerprint` versus the image
  label) and, when appropriate, rebuild with `scripts/docker-test.sh --build`
  before suspecting the environment.
- Keep the image self-contained; do not rely on host Node or host tooling.
- For changes affecting a Concourse task, also verify the affected task with `fly execute` against the working tree on the real worker. Extract its inline config from `concourse/pipeline.yml` (or the live pipeline when reproducing a deployed failure); do not maintain a duplicate task YAML. Local Docker validation does not reproduce task params, history inputs, or worker image access. See `docs/concourse.md` for worker-image considerations.

### Dependabot coverage and the Concourse Node image drift guard

- Dependabot is configured in `.github/dependabot.yml` for four ecosystems: `npm` at `/`, `docker` at `/docker` (which watches `docker/Dockerfile.test`), `github-actions` at `/`, and `ansible` at `/deploy/ansible` (which watches `deploy/ansible/requirements.yml` for the `ansible.posix` collection). Keep all four entries; the `github-actions` entry is what bumps the pinned workflow actions (`actions/checkout`, `setup-node`, `cache`, `upload-artifact`, `download-artifact`).
- Dependabot's `docker` ecosystem only parses Dockerfile `FROM` lines and Kubernetes/Helm `image:` fields. It **cannot** see Concourse `image_resource` tags (`repository: node, tag: ...` in `concourse/*.yml`), so those tags are never bumped automatically. Do not expect a Dependabot PR for them, and do not try to make Dependabot see them by moving the task into a separate `task.yml` — the file format, not the file location, is what Dependabot requires.
- `concourse/node-image.yml` is the single declared source of truth for the Node image tags (`full`, `slim`). `test/concourse-node-image.test.js` (`[INFRA-CI][STORY-71]`) enforces that `docker/Dockerfile.test`, every `concourse/*.yml` task, and the Dependabot `docker` entry all agree with it. When Dependabot bumps the Dockerfile, CI fails until the runtime tags are updated in the same reviewed change.
- When bumping the Node image, update together: `concourse/node-image.yml`, the `tag:` values in `concourse/pipeline.yml` / `tfs-etl.yml` / `ttc-vehicles.yml`, the `node:<tag>` mention in `docs/concourse.md`, and the two pinning tests `test/ci-test-strategy.test.js` and `test/fly-exec-task.test.js` (both assert `24-bookworm-slim`). Then rebuild the test image (`scripts/docker-test.sh --build`) and run `npm run verify`.
- Dependabot auto-merges minor and patch bumps for the `npm`, `github-actions`, and `ansible` ecosystems through `.github/workflows/dependabot-auto-merge.yml`; major bumps always remain open as a PR for manual review. `dev` is intentionally left unprotected (promotion to `main` still flows through a protected PR). Auto-merge depends on `dependabot/fetch-metadata` to classify the update type and uses `gh pr merge --auto --rebase`, which schedules the merge for when any required checks go green and therefore requires branch-protection required status checks on `dev` to gate it correctly.
- The `docker` ecosystem is **never** auto-merged, even for minor bumps, because a Dockerfile `FROM node:<tag>` bump must be paired with the Concourse `image_resource` tags in the same reviewed change (see above) or `test/concourse-node-image.test.js` fails CI. The auto-merge workflow explicitly skips `docker` for this reason. `npm`, `github-actions`, and `ansible` also group by `update-types` (`minor`, `patch`) so minor/patch land in one grouped PR while majors arrive as a separate PR; `docker` is not type-grouped so it keeps its current grouping behavior. Review major bumps (for example a `github-actions` major tag like `6` → `7`) before merging, since they can change workflow behavior. Merging a Dependabot PR into `dev` promotes it to `main` through the normal protected promotion flow.
- Renovate was removed; Dependabot is the sole bump tool, but it still cannot see the Concourse inline `image_resource` tags or `concourse/tfs-etl.yml: NPM_VERSION`. As a safety net for the case where a `docker` Major bump is merged without updating Concourse, `scripts/check-node-drift.js` + `scripts/node-drift.js` (and `.github/workflows/node-drift.yml`, scheduled daily / `workflow_dispatch`) compare `docker/Dockerfile.test`'s `FROM node:<tag>` against `concourse/node-image.yml` and the task tags and open a GitHub issue (deduplicated by a stable title) rather than failing CI. The guard `test/concourse-node-image.test.js` remains the hard on-push failure.

## Required tests and coverage

- Before considering implementation complete or recommending push or promotion, all required tests must pass.
- Coverage must be exactly:
  - 100.00% lines
  - 100.00% branches
  - 100.00% functions
- Do not treat passing tests as sufficient when coverage is below 100%.
- Run `npm run verify` (the canonical full-verification command) before push or promotion when a change can affect covered code; it includes the `docs/validation.md` Docker coverage command.
- `npm run verify:fast` does not satisfy the 100/100/100 coverage requirement; only `npm run verify` (or the `docs/validation.md` Docker coverage command) does.
- Files under `test/fixtures/` are helpers and are not selected as standalone tests by the canonical runner. Imported fixture modules may still appear in Node's coverage accounting; do not infer final coverage from a targeted test run. The full Docker coverage gate is authoritative.
- If coverage is below 100%, identify and report the exact file, uncovered line(s), branch(es), or function(s).
- If the branch gate fails intermittently, inspect short-circuit `||`/`&&` operands for missing deterministic tests. V8 coverage accounting can vary for an unexercised operand; add a meaningful regression for the reachable behavior rather than rerunning until the gate passes.
- Diagnose a coverage gap from lcov, not the summary percentage. `scripts/docker-test.sh sh scripts/run-unit-tests.sh --gaps` runs the canonical offline suite with the lcov reporter and prints only the uncovered line/branch/function records grouped by file (a branch-taken record ending in `,0` or `,-` is the uncovered branch). The scratch report lives under the container's `/tmp`, never the read-only mounted tree. Cross-reference the reported line with `nl -ba` to see the exact expression. Before assuming subprocess coverage is missing, check the enclosing guard's `DA` hit counts: if the guard body has hits, the subprocess coverage is already merged and the real gap is a branch no invocation reaches.
- A spawned CLI's coverage is not reliably merged by the Node test runner, and even when it is, it only exercises the path that invocation takes. Any CLI entry point containing a branch with two observable outcomes (a ternary message, an `if`/`else`) should have its body extracted into an exported function with injectable dependencies (for example `publish`, `log`) so both sides are testable in-process. Keep the entry-point guard itself (`if (isDirectInvocation())`) as a single always-taken path; only extract bodies whose branches produce different observable outcomes.
- Add meaningful tests for reachable behavior.
- Remove only genuinely dead or unreachable code.
- Do not add artificial execution paths solely to satisfy coverage.
- When a live-source integration test fails during verification, probe the endpoint once before re-running the suite (for example `curl --max-time 20 <feed-url>`). If the probe also times out, it is an upstream outage, not a repository failure; record it and move on instead of burning reruns.
- Before committing, run `npm run verify`, which covers the canonical offline unit suite in America/Los_Angeles, the same canonical offline suite in UTC with the 100/100/100 coverage gate, the live-source integration suite, browser JavaScript syntax checks, applicable lint checks, and `git diff --check`. The UTC coverage job is also the UTC unit-suite execution, so there is no separate redundant UTC unit job.

### Test-to-requirement traceability

- Every test is classified as either a `STORY-*` delivery increment or an explicit `INFRA-*` area. This is a traceability layer with an explicit infrastructure bucket, not a forced 1:1 mapping; a large fraction of tests are tooling, not product.
- Requirement IDs come from the canonical roadmap and are reused verbatim: `STORY-<n>` (delivery increment, e.g. `STORY-41A`). A test may carry several.
- Infrastructure tests use one of the enumerated `INFRA-*` areas from a fixed allow-list validated by the checker:

  | `INFRA-*` area | Covers |
  |---|---|
  | `INFRA-DOCKER` | Docker test image and the working-tree wrapper |
  | `INFRA-VERIFY` | The `npm run verify` orchestration |
  | `INFRA-CI` | CI strategy, promotion, and pipeline configuration |
  | `INFRA-PUBLISH` | Data publication and the R2 sink |
  | `INFRA-BROWSER` | Playwright browser suites and the runner |
  | `INFRA-ASSETS` | Frontend asset versioning and cache busting |
  | `INFRA-PWA` | PWA metadata, manifest, and install scope |
  | `INFRA-WATCH` | Watch backend and notification delivery |
  | `INFRA-TTC-PIPELINE` | TTC capture and geometry pipeline |
  | `INFRA-LINT` | ESLint, Ruff, ShellCheck, and syntax checks |
- Put the ID(s) at the start of the test name in brackets, e.g. `test("[STORY-4] nearby summary counts calls within radius", ...)`; stack multiple IDs, e.g. `test("[STORY-28][INFRA-CI] saved locations ...", ...)`.
- `test/requirements.map.json` is the authoritative test-file → `[IDs]` map (many-to-many) and also declares the valid PRD ID space in its `requirements` array (the roadmap is git-ignored and not available inside the Docker test mount, so the ID space is tracked here). The checker cross-validates the map against the IDs in test names: every ID in a name must appear in that file's map, and every mapped ID must appear in at least one name in that file. The checker's own test file (`test/requirement-coverage.test.js`) is exempt from the name/map cross-validation because it necessarily embeds example ID literals, but it must still be mapped.
- `test/requirements.pending.json` is the only exemption mechanism: a bounded, explicit allow-list of not-yet-tagged files. The checker fails if a file is neither tagged nor pending, and fails if a pending file is fully tagged but still listed. The list shrinks as tagging completes and is deleted when empty.
- `scripts/check-requirement-coverage.js` enforces this and runs as a required job in `npm run verify`. Its report of PRD requirements with zero tests is the obsolete-code signal; removing that code is a separate follow-up, not part of a tagging increment.
- Tag tests story by story (one roadmap story per increment) to keep diffs small and reviewable. Do not retag unrelated tests in the same change.
- Tests run inside the Docker test image, which mounts only `src`, `scripts`, `test`, `data`, `concourse`, `.github`, `assets`, `docker`, and the root entry files (see `scripts/docker-test.sh` `MOUNT_DIRS`/`MOUNT_FILES`). `docs/` is **not** mounted and is excluded by `docker/Dockerfile.test.dockerignore`, so a test must not read a file under `docs/`; assert against a mounted path instead.

## Deterministic fixtures and regression tests

- Features or bugs involving external, live, timing-sensitive, browser-specific, or otherwise nondeterministic state must have a deterministic local fixture or test path when practical.
- Keep fixture/test-only behavior clearly separated from production behavior.
- Guard test-only fixtures so they cannot accidentally activate in production.
- In `assert.throws`/`assert.rejects` cases, mutate a named artifact variable and pass the artifact itself — never inline `mutate(artifact())`, whose return value is the mutation result (often falsy), which can silently fail every case at a top-level check while the test passes (Story 76's schema cases did exactly this until the coverage gate exposed it).
- Tests that exercise a publication phase's **default** sink must be environment-independent: inject a deterministic sink (or supply the `R2_*` credentials explicitly) so the phase does not depend on ambient credentials. R2 is the only publication target since the git `data` branch was retired in Story 55E; the default sink is built lazily and fails loudly when the four `R2_*` values are missing, so a fresh skip never requires credentials.
- Cover meaningful states such as:
  - normal data
  - zero results
  - unavailable/failure
  - stale or retained data where applicable
  - update/change state where applicable
- For regressions, reproduce the real failure sequence when practical and add a test that would have failed before the fix.
- Prefer structural and invariant assertions over brittle screenshot-only tests.
- For browser/rendering bugs, assert against actual rendered DOM, geometry, or state where possible.
- Wait for asynchronous rendered state with a bounded Playwright predicate rather than a fixed sleep (for example, Story 39A waits for the expected selected card before checking connector invariants). Diagnose browser startup failures using the shared timing spans before changing timeout or retry behavior.
- The rendered-browser suites have two distinct cold-start waits. The shared `awaitFixtureReady` (`scripts/lib/browser-fixture.js`) waits for `incidentLoadState === 'ready'` with a 60 s budget and one reload retry. Post-readiness UI predicates that gate an assertion (for example the selected-incident card the app marks `.selected` during an async render pass) use the companion `awaitUiState(page, predicate, options?)` — a 5 s per-attempt budget with one bounded retry (Story 70). Use `awaitUiState` rather than a bare `page.waitForFunction` with a short fixed timeout. The Story 68D "cold-start `fixture-ready` timeout class" refers to the shared helper exhausting its 60 s budget under 7-way concurrency (an environment-only artifact; concurrency stays rejected), not to the short UI predicates.
- To exercise a real production timer (for example the app's `setInterval(..., 60000)` minute tick) without a wall-clock wait, use Playwright clock emulation: call `page.clock.install({ time })` **before** `page.goto`, let the page load naturally, then advance with `page.clock.runFor(ticks)` to fire the due timers deterministically. Do not use `page.clock.pauseAt(<captured Date.now()>)` — the fake clock advances past the captured value and `pauseAt` fails with "Cannot fast-forward to the past". Install the clock only on the isolated page that needs it, so other pages keep real time and Leaflet/fixture readiness are unaffected. The TTC diversion list (`#observedDiversions`) is visible only in Calls view, so a clock-emulated TTC scenario must load with `mobileAuditView=calls`.

## Mobile and browser validation

- Playwright Chromium regression testing is required when a change affects rendered layout, geometry, stacking, hit targets, pointer/touch interaction, responsive breakpoints, or browser-driven UI state transitions. Node DOM/string tests and JavaScript syntax checks do not replace it.
- Use `npm run test:browser` for applicable story-completion validation. It discovers every `test:*:browser` package script (excluding itself), starts and readiness-checks the deterministic loopback server on port `8765`, runs the suites sequentially in deterministic order, and tears down its server and child processes on success, failure, or interruption. Do not leave a manual port-8765 server running. A targeted `test:*:browser` script may be used during implementation. The browser suites are not part of the default Docker, CI, `npm run verify`, or `npm run verify:fast` suites; do not probe the Docker test image for Playwright or Chromium. Follow the `docs/browser-tests.md` setup instead.
- The rendered-browser suites run on the **host**, not in the Docker test image (the image has no Playwright/Chromium), so their resource envelope is the host under its existing background load. Each suite launches its own Chromium against the shared read-only `127.0.0.1:8765` server. Browser-suite **concurrency was measured and rejected** (Story 68D): the sequential aggregate is 88-99 s and every concurrent variant was slower (TTC + one other 99-120+ s; all seven small suites at once >120 s with 5/7 failing on cold-start `fixture-ready` timeouts). Keep the sequential runner. When reading `BROWSER_TIMING=json`, the runner's `suite:<name>` span wraps the whole `npm run <suite>` process, but a suite's own internal spans (`page-goto`, `fixture-ready`, `chromium-launch`, `browser-close`) do **not** cover its assertion bodies, so the span total understates the suite wall-clock.
- `npm run test:browser` includes the TTC UI suite, which exercises the app's real minute-based summary refresh with Playwright clock emulation (`page.clock`) rather than a wall-clock wait. Missing local Playwright or Chromium is an outstanding validation requirement, not permission to mark a browser-relevant story `DONE`.
- To preview the app locally with live public data, use `python3 scripts/preview-server.py` (default `http://localhost:8766`). The public feed does not send a CORS header permitting a localhost origin, so a plain static server cannot load live data; the preview server serves the repository and proxies only the two public JSON feeds through the same origin. It is a development-only path that binds to loopback and does not change deployed configuration, and it is not evidence that live-feed CORS is fixed. Use `--port` to change the port.
- The deterministic fixture URL catalog is `docs/fixtures.md` (incident audit states, TTC fixture modes, UX reliability delays, browser-suite contracts). Use it instead of reverse-engineering query strings from the suites.
- `node scripts/visual-probe.js [fixture-url]` is the committed rendered-browser geometry probe (headless Chromium against the preview or deterministic server; clicks a TTC sign marker and prints the computed popup geometry). Use it for visible-acceptance checks before asking the developer to look at a screen.
- If a relevant browser regression does not yet have a Playwright script, add or extend a deterministic rendered-browser regression that asserts DOM state, geometry, and interaction rather than relying only on screenshots.
- New map-layer or chrome UI (legend keys, badge glyphs, status cues, popups) must include a mobile-breakpoint assertion in its rendered-browser regression from the start, not as a follow-up. A desktop-only suite gives false confidence: Story 75's police badge glyph passed at 1280×800 while Story 40D's mobile `label > span > span` clip rule hid it below 680 px until a 440×965 assertion was added.
- Story 75 precedent: a rendered Chromium mobile-breakpoint assertion is necessary but not sufficient for WebKit — the police legend glyph passed Chromium at 440×965 yet failed on real iPhone Safari because WebKit misrenders `::before` content on an empty inline-flex child (it drops to a new line). Decorative glyphs/emoji in a flex legend must be real text content (like the road `⛔` / TTC `🚧` glyphs), not `::before` on an empty element.
- Automated Chromium success does not replace physical-device validation when the reported defect is specific to iPhone Safari, Brave, WebKit, or another browser/device environment.
- `aria-hidden` does not remove an element's text from Playwright's `getByLabel` (a wrapping `<label>`'s full text content is matched). To keep an exact accessible name when adding decorative text inside a wrapping label, set `aria-label` on the associated control (the checkbox `input`), not on the `<label>` — a label-level `aria-label` makes `getByLabel` match both the label and its control (a strict-mode double-match).
- If physical-device validation is still outstanding, report the story as implemented or awaiting validation rather than fully complete.
- Preserve user-selected state during asynchronous loading, refreshes, and deferred UI work.
- Cancel stale deferred work when newer user interaction supersedes it.
- Avoid unnecessary rerenders, refetches, recalculations, and unbounded rendering behavior.

## SirenTO trust and data semantics

Preserve these product semantics in both logic and UI:

- Zero results does not mean source unavailable.
- Source unavailable does not mean zero results.
- Marker aging does not mean an incident is resolved.
- `NEW` or `UPDATED` does not mean severity.
- Number of responding units does not mean danger or severity.
- A police call is not confirmation that a crime occurred.
- Call density is not crime density or neighbourhood safety.
- Do not infer causality between TTC disruptions, road closures, emergency incidents, or other events unless an authoritative source explicitly establishes it.
- Do not infer geographic precision from free-form text.
- If TTC geography cannot be resolved from structured data, preserve the alert but do not invent map geometry.
- TTC stop-ID namespaces (Story 76): alert and Service-Changes feeds reference stops by the complete-scheme stop code, which equals `surfacegtfs.zip`'s `stop_code` column; only surface realtime (bustime) stop IDs match surface `stop_id`. Resolve alert stops through `buildStopCodeLookup` (code-keyed), never `stop_id`, and keep the Story 30C correlation path `stop_id`-keyed.
- TTC static-feed archive layout (Story 77): `surfacegtfs.zip`'s member layout is NOT a contract — members have shipped top-level and nested under a folder prefix (the city's `GTFSExport - Copy/` on 1 Nov 2026). Match members by basename and reject duplicate basenames; never pin the current layout.
- Clearly distinguish SirenTO-observed or inferred information from official-source information.
- Preserve zero, stale, unavailable, and retained-data semantics when changing UI or data flow.

## Repository hygiene

- Do not commit unrelated generated files, screenshots, debug artifacts, temporary credentials, local fixture output, or accidental `data/current.json` changes.
- Before full lint, inspect ignored `tmp/` content for stale repository debug scripts. Never clear `tmp/` indiscriminately: delete only files confirmed to be unreferenced debris, and record that cleanup in the roadmap.
- Prefer the git-ignored `.cache/` directory for repository-local scratch files. Confirm the resolved absolute path before relying on a scratch file; some file tools have resolved `/tmp` requests to the workspace `tmp/` directory.

- Run `git diff --check` before considering work complete.
- When asked for a commit message, keep it concise, high-level, and user-facing, using literal `-` bullets.

## Safe file editing

- **Mandatory prompt instruction:** Use only `perl -0pi -e` or `python3` heredocs for source/test edits. Never use `single_find_and_replace` or `edit_existing_file` on source or test files; they can reformat the whole file and waste implementation cycles before the changes must be reverted.
- Keep `perl -0pi -e` replacements ASCII-only. Perl reads files as bytes, and a non-ASCII character (or a `\x{...}` escape) in the replacement upgrades the whole string to UTF-8 and re-encodes every byte of the file on write, double-encoding all existing UTF-8 (`Wide character in print at -e` is the tell; observed October 2026 when a `\x{2014}` fix corrupted ~1,100 em-dashes and all emoji in the roadmap, recovered with a utf-8/latin-1 round-trip). For non-ASCII content, use a `python3` heredoc or run perl with `-CSD -Mutf8`, and always re-inspect the file's non-ASCII rendering after the edit.
- The canonical roadmap is `PRD.md` at the repository root, a symlink into the private `my-prds` repo (`my-prds/sirento/PRD.md`). Recreate the symlink before story work on any machine that lacks it; edit through the symlink using a `python3` heredoc and commit PRD updates in `my-prds` only.
- Avoid editor-based or generic edit tools that may open files in VS Code or trigger automatic formatting.
- Do not use `single_find_and_replace`, `edit_file`, or similar tools on source/test files if they may rewrite formatting outside the intended change.
- Prefer surgical, non-formatting edits using:
  - `perl -0pi -e` for small in-place replacements
  - `python3` heredoc scripts for exact insertions/replacements
  - other literal text-editing commands that preserve untouched bytes
- Before and after any edit, inspect `git diff --stat` and `git diff`.
- After renaming or changing a source symbol or string literal, `grep` the test tree (`test/`) for that identifier before running the full gate. Source-text pins live in many test files, and a rename silently breaks pins in files you did not open (Story 75: two stale pins in `test/mobile-map-focus.test.js` and `test/police-boundary-lifecycle.test.js` each surfaced as a separate `npm run verify` failure).
- If a supposedly small change produces large unrelated formatting churn, stop immediately.
- Revert the affected file(s) and re-apply the intended change with a surgical text-editing method.
- Do not keep formatter-generated churn in the final diff unless the task explicitly requires formatting changes.
- Treat unexpected file-wide reformatting as a tooling failure, not as part of the implementation.
- `scripts/ttc-ui-browser.js` contains dense formatting that generic edit tools have expanded into unrelated file-wide changes. Apply exact replacements with a `python3` heredoc or `perl -0pi -e`, and inspect the diff immediately.
- `package.json` must retain its trailing newline. Surgical edits must not introduce a spurious whole-file or final-line diff.
- Browser-executed scripts must declare the browser globals they use in their ESLint global comment when those globals are not supplied by the file's lint environment (for example, `getComputedStyle`). Do not add unnecessary globals or weaken ESLint rules globally, and do not modify ESLint configuration solely to accommodate one browser script.

## Story completion

- Record every change in the canonical roadmap, including at minimum why the change was needed and what was changed; this applies to follow-up fixes and maintenance work, not only completed stories.
- Describe a story's real surface area in the roadmap (files, contracts, tests, tooling), not a one-line feature summary; a "trivial" framing hides the work and causes the next session to underestimate scope. Story 75's "add a badge glyph" actually touched Leaflet control DOM injection, the Story 40D accessible-name contract, a mobile clip rule, source-text pins in three files, a new rendered-browser suite, and an asset/cache bump.
- Do not mark a story `DONE` while a required production, CI, browser, or physical-device acceptance step is still outstanding.
- Use an intermediate status such as `IMPLEMENTED / AWAITING VALIDATION` when appropriate.
- When a SirenTO story is completed, update the canonical roadmap:
  `PRD.md` (root symlink into the private `my-prds` repo)
- For a numbered roadmap increment, update its status-table row, detailed section heading/status, and completion handoff in one pass. The handoff must give the next task enough context to start without chat history.
- Every story retrospective/completion handoff must explicitly assess: (1) out-of-band chore or cleanup stories that should be created rather than expanding the current scope, and (2) durable workflow lessons that should refine `AGENTS.md` or `README.md`. Write `None` when no follow-up is warranted; do not silently omit either assessment.
- At the end of every story, print a clearly labelled **Retrospective** in the final response. Summarize what made the work smoother, what was missing or caused rework, verified local facts that should be carried into the next prompt, proposed out-of-band chore/cleanup stories, and recommended `AGENTS.md`/`README.md` refinements. Write `None` for sections with no findings.
- When a retrospective identifies verified repository-specific facts that would otherwise need rediscovery, add a concise **Known local facts** block to the next implementation prompt. Include only facts relevant to that increment: inherited working-tree files, contract shapes and units, fixture IDs/epochs and compatible helpers, known environment-only failures, exact inner-loop commands, and files owned by later stories. Distinguish stable facts from transient observations, and do not copy stale assumptions forward.
- Before trusting a handoff or summary that reports a state (for example "green" or "a fix is already applied"), verify the claim against the working tree (`git status`/`git diff` plus the specific failing check) rather than proceeding on the assertion. A handoff that describes a fix as applied may be describing intent, not the actual tree; Story 75's handoff reported the legend-glyph refactor as complete while the browser assertion and two source pins still carried the pre-refactor state.
- Do not create or update duplicate roadmap copies elsewhere.
- Prefer a narrowly scoped follow-up or regression story over reopening a completed story with a broad rewrite.
